Chapter 1

The big idea

Your whole project in one picture.

The setting

Smart devices (sensors, cameras, smart plugs) often talk to each other using a messaging protocol called MQTT. Attackers can abuse MQTT, for example by flooding it with traffic or guessing passwords. An intrusion detection system (IDS) watches the traffic and raises an alarm when something looks like an attack.

Modern IDSs often use machine learning (ML): you show a model many examples of normal and attack traffic, and it learns to tell them apart.

The claim you are testing

Published papers say ML detectors catch MQTT attacks with 97–99% accuracy. Your argument is that those tests are too easy, in two ways:

  1. The attacker in those tests does not know the detector exists. A real attacker would adjust their traffic to slip past it.
  2. (Found in Phase 1) The test data overlaps heavily with the training data, so part of the score is memory, not skill.
What the evidence changed

Phase 1 showed the picture is more interesting than "the scores are fake". On packets that really contain MQTT, a detector is genuinely accurate even on an honest split. But it relies on a few shortcut features an attacker can change, such as switching DoS traffic from QoS 1 to QoS 0. So your sharper argument is: accurate, but not robust. Chapter 10 explains it.

Analogy: the exam

A student scores 98% on an exam. Impressive, until you learn two things. First, two thirds of the exam questions were copied word for word from the practice sheet they studied. Second, the examiner never tried rewording a question. Your project asks: what is the student's real score with new questions, and with an examiner who tries to trick them? Then it asks how to train the student to cope.

The four objectives

Phase 1 matters because every later phase compares against it. If the baseline is inflated, the attack and defence results will be measured against a false starting point.

Chapter 2

MQTT in plain words

How the devices talk, and what the dataset columns mean.

Publish and subscribe

In MQTT, devices never talk to each other directly. Everything goes through a central server called the broker. (In Phase 2 you will use a real broker called Mosquitto.)

Packet types you will see

MQTT communication is made of small messages called packets. Each has a type:

PacketWhat it doesType number
CONNECT"Hello, I'm device X, here is my username and password"1
CONNACKBroker's reply: accepted or refused2
PUBLISH"Here is a message for topic Y"3
PUBACK"Got your message"4
SUBSCRIBE"Send me everything on topic Y"8
PINGREQ"I'm still alive" (keep-alive)12
DISCONNECT"Goodbye"14

MQTT travels inside TCP

MQTT messages are carried by TCP, the standard internet delivery layer. TCP also sends its own packets that carry no MQTT content at all, such as acknowledgements ("got it") and connection set-up. Remember this; it matters in chapter 6.

The columns in your dataset, decoded

Each column is one field read from a packet. You will drop 12 of them because they never change. These are the ones that matter:

ColumnPlain meaning
tcp.flagsTCP control bits, written in hex. 0x00000010 = ACK, 0x00000018 = PSH+ACK (data being sent), 0x00000011 = FIN+ACK (closing).
tcp.time_deltaSeconds since the previous packet in the same connection. Captures rhythm: floods are fast, slow attacks are slow.
tcp.lenHow many bytes of data the TCP packet carries.
mqtt.hdrflagsThe first byte of an MQTT packet. The first hex digit is the packet type: 0x30 = PUBLISH (3), 0x40 = PUBACK (4).
mqtt.msgtypeThe packet type as a number (see table above).
mqtt.lenLength of the MQTT message in bytes.
mqtt.msgThe message content itself (the payload). Has 50,054 different values in your data.
mqtt.kaliveKeep-alive: how many seconds the device promises to stay quiet at most before pinging.
mqtt.conflagsCONNECT options in hex. 0x00000002 = clean session. 0x000000c2 = username + password + clean session.
mqtt.conflag.uname, .passwd, .cleansessThe same CONNECT options as separate yes/no columns.
mqtt.conack.val, mqtt.conack.flagsThe broker's answer to CONNECT (accepted or refused, and why).
mqtt.qos, mqtt.retain, mqtt.dupflagDelivery options on PUBLISH: quality-of-service level, "keep this message for new subscribers", "this is a resend".
mqtt.msgidMessage ID number used to match a message with its acknowledgement.
mqtt.protoname, mqtt.proto_len, mqtt.verIn CONNECT: protocol name ("MQTT"), its length, and the version.
Why so many zeros

A PUBLISH packet has no CONNECT options, and a plain TCP acknowledgement has no MQTT fields at all. Whenever a field does not exist in a packet, the dataset writes 0. So 0 often means "not there", not "the value zero". That is why your Task 1 output showed both 0 and 0x00000000 in the same column. Step 2 will keep those two meanings separate.

Chapter 4

Machine-learning words, broken down

The vocabulary you will be asked about.

Training and testing

You split the data into two piles:

  • Training set: the model studies these rows, with the answers.
  • Test set: rows the model has never seen. You hide the answers, ask the model to guess, then compare. This tells you how it will do on new traffic.

The test only means something if the test rows are truly new. If the same rows are in both piles, the model can simply remember the answers. That is the core of your Task 1 finding.

Generalising vs memorising

Analogy

Memorising is learning that "question 7's answer is B". Generalising is understanding why, so you can answer a question you have never seen. We want detectors that generalise, because real attack traffic will never be an exact copy of the training data.

Overfitting

Overfitting is when a model learns the training data too closely, including its quirks and noise, and then does worse on new data. Prof. Yamani's strongest point was that the published 97–99% might be partly overfitting. Your leakage finding is evidence for a closely related problem: when test rows are copies of training rows, an overfitted model is never caught, because the test contains the same quirks it memorised.

Cross-validation

One train/test split can be lucky or unlucky. Cross-validation repeats the test several times on different slices of the training data and averages the results.

Mean ± standard deviation, for example "0.91 ± 0.02" (pretend numbers): the mean is the average score over the 15 rounds; the standard deviation says how much it wobbles. A small wobble means the result is stable. The final test set is used only once, at the very end, never for choosing settings.

Random seed

Shuffling and model training involve randomness. A seed (you use 42) fixes that randomness, so running the code again gives exactly the same numbers. Your two runs today gave identical results; that is reproducibility, which the panel asked for.

Chapter 5

Measuring a detector

Why accuracy lies, and what to report instead.

The accuracy trap

Accuracy = how many guesses were right out of all guesses. It sounds fine, but with imbalanced data it hides failures.

On your real data (derived)

A "detector" that says legitimate for every single packet would score 50.00% accuracy while catching zero attacks. And a detector that never catches a single flood packet loses only 0.19% accuracy, because flood is so rare. Accuracy cannot see rare classes.

The confusion matrix

A table of what the model guessed against what the truth was. Pretend example, 100 packets, three classes:

Truth ↓ / Guess →legitimatedosfloodTotal
legitimate882090
dos2608
flood2002

Green diagonal = correct. Everything else is a mistake. Accuracy here is (88 + 6 + 0) / 100 = 94%, which looks great, yet every flood packet was missed.

Precision and recall, one class at a time

Recall (detection rate)
Of all the real X packets, how many did we catch?
dos: 6 of 8 = 75%. flood: 0 of 2 = 0%.
Precision
When we shouted "X!", how often were we right?
dos: 6 right of 8 shouts = 75%.
F1 score
One number that balances precision and recall. High only if both are high. dos F1 = 75%.
False positive rate (FPR)
Of the normal packets, how many did we wrongly call an attack? 2 of 90 = 2.2%. Too many false alarms and operators switch the detector off.
Analogy: airport security

Recall: of all the passengers carrying a knife, how many were stopped? Precision: of all the passengers stopped, how many actually had a knife? Stopping everyone gives perfect recall and terrible precision. Stopping nobody gives zero false alarms and catches nothing.

Macro F1: your headline number

Macro F1 = work out F1 for each class separately, then take the plain average. Every class counts equally, so a missed rare class drags it down hard.

In the pretend example: legitimate F1 96.7%, dos 75.0%, flood 0%. Macro F1 = 57.2%, far below the 94% accuracy. That gap is exactly why you report macro F1.

On your real data (derived), the "always say legitimate" detector has 50.00% accuracy but a macro F1 of only about 11%. It is useless, and macro F1 shows it.

Weighted F1 averages the per-class F1 scores weighted by class size. It behaves more like accuracy, so you report it as secondary.

Cost metrics (needed for O4)

  • Inference latency: milliseconds the model needs to judge one packet. A small IoT gateway has little CPU.
  • Model size: how big the saved model file is on disk.

Chapter 6

What you found in Task 1

Your real results, explained one at a time.

Finding 1. Most rows are duplicates

A duplicate is a row whose 33 feature values are exactly the same as another row's. 209,499 rows (63.31%) are exact duplicates of another row, label included.

Why duplicates exist (you must be able to explain this)

This is packet-level data. Real traffic is repetitive: a sensor sends the same-shaped message every few seconds; keep-alive pings are identical; an attack tool fires the same packet thousands of times. So the duplicates are not a mistake in the dataset. The problem comes later, when the rows are split randomly into train and test.

Finding 3. Some identical packets have different labels

A label conflict is when two rows have exactly the same features but different labels.

  • 1,129 distinct feature vectors carry more than one label.
  • They cover 110,711 rows (33.45%).
  • slowite has no conflicts at all.
Do not say "a third of the data can't be classified"

That is wrong. Pretend example: a feature vector appears 1,000 times as legitimate and 5 times as dos. A model that always answers legitimate for it gets 1,000 right and only 5 wrong. Only the minority rows are lost.

Finding 4. The ceiling: 94.38%

Counting only those unavoidable minority rows across the whole file gives 18,594 rows (5.62%) that no model can get right with these features. So the best possible accuracy is 94.38% on this file with these 33 features.

Three limits on the 94.38% figure
  1. It covers the whole file. A specific test split could have a slightly different ceiling; not measured.
  2. It applies to mqttdataset_reduced.csv with these 33 columns. Papers that report 97–99% may have used a different MQTTset file or different features. You must check what each paper used before comparing.
  3. It changes in Step 2. On the final 20 features it is 93.27% (chapter 9).

Untested guess about the cause: many conflicting rows may be plain TCP packets (acknowledgements, connection set-up) with no MQTT content, so all MQTT fields read 0. Such packets look the same in every capture, but each one gets the label of the capture file it came from. Step 2 will test this.

Chapter 8

The three models

Three kinds of learner, chosen to be small enough for a laptop CPU.

Random Forest

A decision tree is a flowchart of yes/no questions: "Is mqtt.msgtype = 1? Is mqtt.kalive over 60?" until it reaches an answer. A random forest grows 100 trees, each on a slightly different random sample of the data, and lets them vote.

XGBoost

Also builds many trees, but one after another: each new tree focuses on the mistakes the previous trees made. It is often the strongest model on table-shaped data like yours.

MLP (a small neural network)

A multi-layer perceptron passes the 21 feature values through two layers of "neurons" (64, then 32), which combine them into an answer. It represents deep learning, kept small for your CPU. It needs scaled inputs: every feature rescaled to a similar range, so a big number like a byte count does not drown out a small one like a flag.

Feature importance

Tree models can report which features they relied on most. This matters for Phase 2: a feature that is both important and changeable by the attacker is the first thing an attacker will tweak.

  • 20 features are used: 33 minus 12 constant columns minus mqtt.msg.
  • Hex text becomes a number. A plain 0 ("field not in this packet") becomes −1, so it is not confused with a real zero.

The guess about conflicts was right

Of the rows whose features also appear under another label, 99.89% have no MQTT header at all. They are bare TCP packets (acknowledgements, handshakes) that look the same in every capture. Each one got the label of the capture file it came from. That is how MQTTset was labelled, so you report it as a limitation of the dataset.

A hidden giveaway in mqtt.msg

Every slowite row, and no other row, writes its payload as 0.0. All the others write 0. That is a formatting accident, not attack behaviour, but a model reading the text could use it to spot slowite perfectly. It is a second reason for dropping mqtt.msg.

New ceiling: 93.27%

On the 20 final features, 6.73% of rows are unavoidable errors, so no model can beat 93.27% accuracy on this data. Leakage in the published split rises to 69.59% of test rows, and for legitimate to 98.43%.

The surprise: the leaky split scored lower

You expected A, with all its leakage, to look better. It looks worse. The reason is that A's test set is really three different groups mixed together:

So memorisation is real (a third of the published test set is answered almost perfectly because it was in training), but in this dataset an even bigger block of ambiguous packets pulls the score down. Variant B keeps only one row per (packet shape, label), so those repeated ambiguous packets almost disappear. That is why B scores higher. The A − B gap mixes two opposite effects, so it is not a measure of inflation. The three-group table is.

Class weights: a trade-off

"Balanced" class weights tell the model that rare classes matter more. On Variant A that pushes the ambiguous packets towards rare classes: more flood caught, but many false alarms (14.5% of normal traffic flagged). Without weights, XGBoost on A reaches 92.34% accuracy, close to the 93.27% ceiling, with only 1.29% false alarms, but it catches fewer rare attacks. You report the weighted version as planned and the unweighted one as a sensitivity check.

The message ID clue (for Phase 2)

XGBoost's most important feature on B is mqtt.msgid. It is 0 in every legitimate, flood, slowite and bruteforce row, but non-zero in most dos rows. MQTT only adds a message ID when a message is sent with QoS 1 or 2, so in this dataset DoS traffic uses QoS above 0. An attacker can simply choose QoS 0. That is a ready-made evasion to test in Phase 2.

Cost (for O4, measured on your Mac)

  • XGBoost: about 1.1 MB, about 0.10 ms per packet. Best balance.
  • Random Forest: 42–49 MB, about 3 ms per packet.
  • MLP: about 124 KB, about 0.16 ms per packet, but the least accurate.

Unreliable: flood has only 94 (A) and 80 (B) unique test packets, below the 100 line, so its per-class scores are marked unreliable.

Questions you may be asked

Is the dataset labelled? Is it balanced?

Labelled, yes: every row has a target label with six classes. Not balanced: legitimate is 50% and flood 0.19%, about 270 to 1.

Aren't the duplicates just bad data? Why not delete them?

They are real: network traffic repeats. Deleting them would change the real-world class mix. The problem is only that a random split puts copies on both sides. So I keep Variant A as published, and in Variant B I keep all copies of a packet on one side of the split.

How do you know your leakage number is right?

It compares every row of the full test file against every row of the full training file, exactly, not a sample. The script is in the repository and gives the same answer every run.

Why not report accuracy?

With this imbalance, a detector that always says "legitimate" gets 50% accuracy and catches nothing. Macro F1 weights every class equally, so a missed attack type shows up.

Are you saying published papers are wrong?

No. Most of the 99% MQTT papers I read use a different dataset, MQTT-IoT-IDS2020, so my MQTTset ceiling does not apply to them. The one MQTTset paper I have drops the two hardest classes and never handles duplicates. And on MQTT packets alone, I find detection genuinely is very accurate. My point is that it relies on features an attacker can change.

Why use only MQTT packets in Phase 2?

Bare TCP packets have no MQTT fields for an attacker to change, and they are labelled by capture file, so they cause 99.89% of the label conflicts. Without them the honest baseline is strong (macro F1 0.979), so any drop under attack is meaningful. The cost is that the detector no longer looks at TCP-only traffic, which I report as a limitation.

Isn't removing the bare TCP packets just making your results look better?

I report both. The all-rows results stay as the Phase 1 finding about benchmark quality. The MQTT-only population is chosen for Phase 2 because the attacks change MQTT fields, and I state that choice and its cost openly.

Why did the leaky split score lower than the honest one?

Its test set mixes three groups: memorised packets (about 100% right), ambiguous bare TCP packets with conflicting labels (much lower), and new packets. The ambiguous group outweighs the memorised one. The de-duplicated split removes most repeats of the ambiguous packets.

Why is message ID the top feature?

Only QoS 1 or 2 messages carry an ID, and in this dataset only DoS traffic uses QoS above 0. It is real protocol behaviour, but an attacker can choose QoS 0, so it is an obvious target for Phase 2.

Why not use SMOTE to fix the imbalance?

SMOTE creates synthetic rows by blending real ones. A blended MQTT packet may not be a valid packet, which contradicts my project's whole argument about staying protocol-valid. So I use class weighting instead and report per-class scores.

Chapter 12

Test yourself

Answer out loud before you open each one. If you get stuck, reread the chapter in brackets.

1. What is one row of your dataset? (ch. 3)

One network packet, described by 33 feature columns and labelled with one of six classes in target.

2. What does the broker do in MQTT? (ch. 2)

It receives every published message and forwards it to the devices subscribed to that topic. Devices never talk directly.

3. Why can 0 in an MQTT column be misleading? (ch. 2)

It often means the field does not exist in that packet type, not that its value is zero.

4. Recall vs precision, in one line each. (ch. 5)

Recall: of the real attacks, how many did we catch. Precision: of our alarms, how many were real.

5. Why is macro F1 your headline and not accuracy? (ch. 5)

Macro F1 weights each class equally, so missing a rare class like flood shows up. Accuracy hides it.

6. What is leakage, and how much is in the published split? (ch. 6)

Test rows that also appear in training. 66,432 of 99,290 test rows, 66.91%.

7. Why are there so many duplicates? (ch. 6)

Packet-level traffic is repetitive by nature. The duplicates are real, not errors.

8. What is a label conflict, and why can't a model fix it? (ch. 6)

Identical features with different labels. The model only sees features, so it must give both rows the same answer.

9. What does 94.38% mean, and what are its limits? (ch. 6)

The best possible accuracy on this file with these 33 features, because 5.62% of rows are unavoidable errors. It is for the whole file, only this file and feature set, and will change after Step 2.

10. What is the difference between Variant A and B? (ch. 7)

A uses the published split with its leakage. B keeps one row per packet shape and label, split so the same shape is never on both sides, so the test is truly unseen.

11. Random Forest vs XGBoost in one line each. (ch. 8)

RF: many independent trees vote. XGBoost: trees built one after another, each fixing earlier mistakes.

12. Why does Phase 2 care about feature importance? (ch. 8, 10)

Features that are important and changeable by the attacker are the ones an attacker will tweak first.

13. Why did Variant A score lower than B? (ch. 9)

A's test set mixes memorised packets (about 100% right), ambiguous bare TCP packets (much lower) and new packets. The ambiguous block pulls it down more than memorisation lifts it.

14. Give two reasons for dropping mqtt.msg. (ch. 9)

The model could memorise payload content, which the attacker fully controls; and every slowite row writes it as "0.0", a formatting giveaway.

15. What is the best model, and what is its honest score? (ch. 9)

XGBoost: macro F1 0.8673 on Variant B's held-out test set (0.8662 ± 0.0174 in cross-validation). Small (about 1 MB) and fast.

16. Why can't you quote 93.27% against most 99% MQTT papers? (ch. 10)

Most of them use MQTT-IoT-IDS2020 or other datasets. The ceiling was measured on MQTTset with these 20 features only.

17. What happens on MQTT packets only? (ch. 10)

Label conflicts fall from 34.89% to 0.06%, the ceiling rises to 99.98%, and XGBoost reaches macro F1 0.9792 on an honest split.

18. What is a shortcut feature? Give your best example. (ch. 10)

A feature that separates the classes in this dataset but an attacker can change. Example: every DoS PUBLISH uses QoS 1 and every normal one QoS 0, and QoS is the sender's choice.

19. Name one "dependent" feature and its rule. (ch. 10)

mqtt.conflags = 128·uname + 64·passwd + 2·cleansess. Or mqtt.hdrflags = 16·msgtype + the PUBLISH flag bits.

20. Why is malformed handled separately in Phase 2? (ch. 10)

Malformed traffic breaks the protocol on purpose, so the rule "stay protocol-valid" cannot apply to it.

Chapter 13

Glossary

Quick lookup.

Adversarial / adaptive attacker
An attacker who knows a detector exists and changes their traffic to slip past it.
Broker
The central MQTT server every message passes through.
Class
One possible label value, for example dos.
Class imbalance
Some classes have far more rows than others (here about 270 to 1).
Confusion matrix
Table of true class against predicted class.
Constant feature
A column that has the same value in every row; useless for learning.
Cross-validation
Repeating train-and-check on different slices of the training data and averaging.
Duplicate
A row whose features are identical to another row's.
Error floor / ceiling
The share of rows no model can get right (5.62%), and so the best possible accuracy (94.38%).
Feature
One input column describing a packet.
Feature vector
All the feature values of one row together.
F1 / macro F1 / weighted F1
Balance of precision and recall; plain average over classes; average weighted by class size.
False positive rate
Share of normal traffic wrongly flagged as attack.
Generalise
Do well on data the model has never seen.
Hex
Base-16 numbers like 0x00000018 (= 24 in normal counting).
IDS
Intrusion detection system: watches traffic and raises alarms.
Inference latency
Time a trained model takes to judge one packet.
Label
The correct answer for a row (target).
Label conflict
Identical features, different labels.
Leakage
Test rows that also appear in training, so the test is not really unseen.
Overfitting
Learning the training data's quirks so closely that performance on new data suffers.
Precision
Of the alarms raised for a class, the share that were correct.
Recall
Of the real rows of a class, the share that were caught.
Reproducible
Running the same code on the same data gives the same numbers.
Scaling
Rescaling features to similar ranges; needed for the MLP.
Seed
A fixed number (42) that makes random steps repeatable.
Standard deviation
How much results wobble across repeated runs.
Stratified
Splitting so each part keeps the same class mix.
Test set / training set
Rows held back for the final check / rows the model learns from.
Bare TCP packet
A TCP packet with no MQTT content, such as an acknowledgement or handshake. 37% of MQTTset rows.
Constraint (O2)
A rule an adversarial change must obey to keep the packet valid MQTT and the attack working.
Dependent feature
A feature calculated from others, so it changes only when they do.
Mosquitto
A widely used open-source MQTT broker; your Phase 2 testbed.
QoS (quality of service)
MQTT delivery level: 0 = send once, 1 = confirm delivery, 2 = exactly once. Chosen by the sender.
Shortcut feature
A feature that separates classes in a dataset for a reason an attacker can easily change.
